## 1. Deviation 1 (round-then-ceil) — accepted, and your criticism was UNDERSTATED

You said my `GATE_EPSILON = 1e-6` "silently breaks again around ~85 objectives." I brute-forced both
implementations against exact decimal arithmetic over every two-decimal fraction, totals 1..20,000:

| | first total where it disagrees with exact decimal |
|---|---|
| **my epsilon subtraction** | **45** (at fraction 0.6). 153 disagreements within totals 1..200 alone. |
| **your round-then-ceil** | **1,750** (at fraction 0.72). **Zero** disagreements anywhere in 1..1,000. |

So it is worse than you reported: not ~85, but **45** — and Khost has 42 strongholds. A scenario that made
every stronghold an objective would land on the bug. I would have shipped a constant tuned to the objective
counts in front of me and called the tuning a design decision.

`Math.Round(product, 4)` is the better answer for exactly the reason you give — it removes the noise
proportionally instead of absolutely, so it does not need to know how big `total` might get. **Adopting the
same technique in the editor's E15 mirror** rather than porting my epsilon across.

⚠ One note for the file, not a change request: `Math.Round(double, int)` is banker's rounding, which is
*harmless here* — the product of a two-decimal fraction and an integer, plus ≤1e-5 of float noise, can
never sit on a 4-decimal midpoint. Worth a half-line in the comment so nobody "fixes" it to
`AwayFromZero` later and quietly changes the boundary behaviour.

## 4. THE ONE OPEN ITEM — the auto-end invariant is still a comment, not an assertion

**Not blocking. Your call. I am raising it because it is the one place my ask went unmet, and dropping it

Your structural argument is legitimate **as far as it goes**: one helper, three call sites, a doc comment
forbidding inlining — that makes *divergent arithmetic* unrepresentable, which was my main worry, and the
composition tests pin the grader both ways.

What it does not cover is a call site that **stops consulting the helper at all, or inverts the polarity**.
Neither is caught by any test today, and one of them has the worst blast radius in this pass: a battle that
auto-ends at a decisive share with the gate unmet, then grades capped. Your own comment calls that out —
*"the battle must never auto-end at a rung the gate would then deny"* — and it is currently enforced by
that sentence.

**A ~20-line extraction closes it, using the pattern this file already uses four times** (`GradeBattleResult`,
`ComputeIncome`, `ComputeEarlyFinishBonus`, `AuditLadderReachability` are all pure `internal static`
precisely so EditorTests can reach them):

```csharp
/// <summary>V10.2/C7 — may the player end voluntarily? Pure, for EditorTests.</summary>
internal static bool MayEndEarly(VictoryLedger ledger, float minorCut, bool gateMet)
    => minorCut > 0f && ledger.TotalValue > 0f && gateMet && ledger.PlayerShare >= minorCut;

/// <summary>V10.1 — nothing further to gain: top rung AND the gate. Pure, for EditorTests.</summary>
internal static bool ShouldAutoEnd(VictoryLedger ledger, float minorCut, float decisiveCut, bool gateMet)
    => minorCut > 0f && ledger.TotalValue > 0f && gateMet && ledger.PlayerShare >= decisiveCut;
```

`CheckVictoryConditions` (1204) becomes its guard plus one return; `OnEndScenarioButton` (1147) keeps both
UI strings — they distinguish "not scored" from "not achieved" for the player, which a single bool would
flatten — but takes its *permission* from `MayEndEarly`:

```csharp
bool gateMet = MissionObjectiveGateMet(map, MissionObjectiveFraction);
if (!MayEndEarly(ledger, VictoryThresholdMinor, gateMet))
{
    AppService.CaptureUiMessage(VictoryThresholdMinor <= 0f || ledger.TotalValue <= 0f
        ? "This scenario is not scored — it runs to the turn limit."
        : "Cannot end the scenario — victory has not been achieved yet.");
    return;
}
```
